db-agent: architecture and workflows

Ask PostgreSQL, MySQL, MariaDB and an Oracle 19c Data Guard pair questions in plain English. Everything runs with Docker Compose on one Linux VM. Four pictures, each with what to take away from it. Setup steps are in SETUP.md; the Oracle lab in ORACLE-LAB.md.

1 · Architecture

Three layers. The Python app (your terminal or the web UI) runs the LangChain agent and talks to the model over HTTPS. For data it never touches a database directly: it calls the MCP Toolbox for that database, and the Toolbox runs SQL with a read-only login. The Oracle lab adds a primary and a physical standby; the agent's Toolbox connects to the primary only.

  • One Toolbox per database because the built-in tool sets reuse names (execute_sql, list_tables).
  • Read-only is enforced by the database, not by the prompt: agent_reader / C##AGENT_READER cannot write.
  • The web UI has no login: it listens on the VM only, and you reach it through an SSH tunnel.
  • Model choice is per session; oracle_prod refuses external models unless you allow it for the lab.

2 · What happens when you ask a question

The agent is a loop: the model chooses a tool, the app runs it through the Toolbox, the result goes back to the model, until the model can answer. For oracle_prod the prompt carries a Data Guard runbook from app/databases.toml, so the model knows which tools to call first and what counts as a problem.

  1. The model only sees tool descriptions and results. Passwords stay in .env and the Toolbox.
  2. Custom tools (all 30 Oracle ones) are fixed SQL: the model supplies values, never SQL. Free-form SQL goes through execute_sql, capped at 4 per question.
  3. The answer names the database and lists the tools used, so you can check the evidence.

3 · How the Oracle Data Guard lab builds itself

The first docker compose up takes 30-70 minutes; later starts take about a minute. The two Oracle containers coordinate through a small shared volume: the primary drops its password file and a primary_ready flag there, and the standby waits for that flag before cloning.

4 · Redo flow, and what the agent can see

Every change on the primary becomes redo. The transport process ships it ASYNC to the standby, which writes it to standby redo logs and applies it in real time (MRP). A mounted standby only accepts SYSDBA/SYSDG logins, so the agent reads everything from the primary, which tracks each standby's status, gaps and applied SCN.

Try it: stop apply on the standby, or stop the standby container, then ask "Is Data Guard healthy?". ORACLE-LAB.md → Break it on purpose has the commands.
